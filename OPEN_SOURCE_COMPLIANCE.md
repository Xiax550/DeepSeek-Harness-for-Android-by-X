# Open-source compliance

This document defines which license applies to which part of DHA and the checks
required before publishing an APK, payload, hot package, or release asset.

## License boundaries

- Original DHA source code and explicitly MIT-authorized project artwork are MIT licensed. The
  upstream copyright notice remains in `LICENSE`.
- Bundled third-party code keeps its own license. MIT does not replace an
  AGPL, GPL, Apache, LGPL, or asset-specific license.
- Retained or historical Coopanion-derived code remains AGPL-3.0-or-later.
  Historical source retains its separate character-art restrictions. The current
  renderer is `payload/opt/dsh/android/ball-web/reference/figure.js`; the new
  reference artwork has separate terms in `ARTWORK_RIGHTS.md`.
- The APK as a combined distribution is not described as "MIT only". It ships
  components under multiple licenses.
- Supplying an image does not establish its redistribution license. New
  reference-derived character assets and the launcher icon require the evidence
  listed in `ARTWORK_RIGHTS.md`; they are not automatically covered by MIT.
- A retained historical AGPL component notice must not be removed merely because
  a new renderer is independent. Review each retained derivative separately.
- The DHA and DeepSeek Harness names and marks are used descriptively. This
  project is unofficial and is not endorsed by DeepSeek.

The dependency versions, origins, purposes, and reproducibility limits are in
`DEPENDENCIES.md`. The detailed component/license inventory is in
`THIRD_PARTY.md`. License texts and source pointers are collected in
`LICENSES/README.md`.

## Release checklist

Before a public app release:

1. Run the unit tests and plugin-profile migration tests.
2. Verify the installed APK version, signature, package name, and launcher icon.
3. Generate and attach the corresponding source archive.
4. Include `LICENSE`, `NOTICE.md`, `DEPENDENCIES.md`, `THIRD_PARTY.md`,
   `OPEN_SOURCE_COMPLIANCE.md`, and `LICENSES/` in the source archive.
5. Confirm that every network-downloaded binary has a pinned checksum and a
   documented source, version, license, and corresponding-source location.
6. Generate an SBOM from the exact final payload, including the full npm tree
   and Ubuntu package inventory; the hand-maintained dependency overview is not
   a substitute for this release-specific inventory.
7. For AGPL components, provide the preferred form for modification and retain
   prominent notices that the app contains AGPL code.
8. Do not claim complete compliance while a component is marked "source
   unavailable" or "unverified" in `THIRD_PARTY.md`.
9. Ship the **per-component license texts** that `THIRD_PARTY.md` points at.
   Both APK packers must copy every file in `LICENSES/` (not only the four SPDX
   texts) into `assets/licenses/`; MIT and PSF licenses require the notice to
   accompany every distributed copy, and the APK is that copy.
10. Verify that the license files embedded in the APK are byte-identical to the
   repository versions (`unzip -p <apk> assets/licenses/THIRD_PARTY.md | cmp - THIRD_PARTY.md`).
   A released APK that ships older texts than the repository is a documentation
   defect and must be rebuilt before the release notes are published.
11. Attach `proot-src-8cf13e99.tar.gz`, generated by
   `scripts/make-proot-source.sh`, next to every release containing the current
   PRoot ELF. A normal project source archive does not include Git submodule
   contents.

This inventory is not a full legal audit or a replacement for corresponding
source. Package license/source obligations still apply, and this project does
not claim that every transitive package has been independently audited.

publishing only the APK is not sufficient.
